# Complete the 0.3.1 wrapper release

Native Swift 0.3.1 is published at
https://github.com/TheBoldApps/notification.dev-SDKs/releases/tag/0.3.1.
Its archive checksum is verified; clean remote-package consumers build for ARM64
simulator and device destinations. Do not replace that tag or archive.

Android 0.3.1 is not yet published to Maven Central. Flutter and Expo 0.3.1 must
wait for that dependency. This branch prepares their pins, package versions,
examples and installation documentation; it is not a completed public release.

## Publish Android first

Use the existing Maven Central account and GPG signing setup described in
[RELEASING.md](../../RELEASING.md). The previous Android 0.3.0 release was signed
by Petr Kubes's key `1465CDE01959C16B2C6D9E1CDB1E5158341C8943`.
Do not commit credentials or private keys.

```sh
./gradlew verifyRelease
./gradlew publishToMavenCentral
```

Validate and publish the deployment in Central Portal. Confirm public POMs,
Gradle metadata and artifacts for all `dev.notification` coordinates at 0.3.1:
`android-sdk`, `sdk-core`, `sdk-core-android`, `sdk-core-iosarm64`,
`sdk-core-iossimulatorarm64`. Test an Android consumer against Maven Central
without local/composite dependency overrides before publishing wrappers.

## Publish wrappers

The native iOS dependency already resolves remotely. Align any direct SDK
reference in the host app/widget with 0.3.1 to avoid Swift Package Manager
conflicts between exact 0.3.0 and 0.3.1 requirements.

From `flutter/`, run analysis, tests, packaging validation and consumer builds
as documented in RELEASING.md. Remove `(unreleased)` from the changelog after
verification and publish with `flutter pub publish`. Check pub.dev installation
and native builds from a clean consumer.

From `expo/`, run npm tests, Ruby SPM tests, inspect `npm pack`, and verify
consumer builds using released native dependencies. Publish the tested tarball
as `@notification.dev/expo@0.3.1` using the existing package maintainer account.
Its currently listed npm maintainer is `kebsu`. Verify the registry package and
native builds after publication. Do not reuse or overwrite 0.3.0.

The product backend bundles SDK guides. After publication, import the updated
guides into notification.dev using its existing `import:sdk-guides` command and
deploy through the normal main-to-dev and production-promotion workflows.

## Verification already completed

- A saturation/recovery regression fails on native 0.2.0 with app-open and
  paywall uploads accepted but the same delivery's open missing. It passes on
  native 0.3.1 with all three uploaded. The fix does not retroactively prove the
  cause of any particular customer's missing interaction.

- `verifyRelease`: 113 Android-host core, 97 iOS simulator core and 12 Android SDK
  tests; release lint and POM validation pass. Native Android AAR builds.
- Native Swift: 37 tests pass. Exact public archive checksum verified.
- Expo: 15 JS tests, 2 Ruby tests / 11 assertions, package inspection, and native
  simulator/device-destination builds against the patched Swift package pass.
- Flutter: analysis and 22 tests pass. The example builds for iOS device with
  code signing disabled, resolving published native Swift 0.3.1.
- Physical production-device notification tap validation remains necessary;
  simulator/build results do not establish customer callback execution.

## Exact consumer compatibility gate

Published Expo wrapper 0.2.0 declares Expo `>=57 <58`; its peer range excludes
Expo 58. Candidate 0.3.1 declares `>=57 <59`. An isolated consumer with Expo
58.0.0, React Native 0.88.0-rc.3 and React 19.3.0 now builds for iOS simulator
and device destinations using public Swift 0.3.1, and Android using locally
built unsigned Maven 0.3.1 artifacts. This verifies compilation of that
consumer, not public Android dependency availability or the customer's full app.
Before calling the coordinated upgrade available, repeat remote-only Android
verification with the final published dependencies and package. Record resolved
native versions and build provenance, and verify physical notification taps.
Source/lockfile versions alone do not establish which code is in an installed binary.
